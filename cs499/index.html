Professional Self-Assessment

Professional Introduction

Completing the Computer Science program and building this ePortfolio helped me turn a broad interest in technology into a focused professional direction. My goal is to work in robotics systems integration, physical AI, autonomous systems, or another role where software must interact reliably with sensors, computing hardware, electronics, communications, and mechanical systems. The program gave me experience across programming, algorithms, databases, security, operating environments, testing, and software design. The capstone required me to bring those areas together, examine my earlier work honestly, improve it in measurable stages, and explain the reasons for my decisions. This process strengthened my ability to present evidence of what I can build rather than only listing technologies on a resume.

Strengths, Professional Goals, and Values

My strongest professional trait is a systems-level approach to problem solving. I am most interested in the final integration stage, where separate components must operate as one complete system. These projects reinforce my professional values of accuracy, honest documentation, safety, privacy, and persistence. They also show that I am willing to learn unfamiliar systems deeply rather than treating one layer in isolation.

Collaboration and Communication

Computer science work is rarely useful if other people cannot understand, review, or operate it. Coursework in the software development lifecycle, design documentation, discussion activities, and code review taught me to connect technical choices to the needs of teammates, managers, users, and other stakeholders. In the capstone, I used a code review to explain existing behavior, weaknesses, and planned improvements before modifying the artifact. I then used separate classes, clear interfaces, focused comments, consistent names, narratives, and a public ePortfolio so another developer can follow the project. My professional and field experience also required customer communication, documentation, scheduling, and responsibility for results without close supervision. Together, these experiences support Outcome 1 by showing strategies that help different audiences participate in decisions, and Outcome 2 by demonstrating professional oral, written, visual, and technical communication.

Data Structures and Algorithms

The program taught me that selecting a data structure is a design decision rather than a syntax choice. In the capstone, I replaced position-based client handling with stable IDs and an unordered_map for average O(1) lookup. I used vectors when an ordered sequence was needed and std::sort for O(n log n) views by ID, name, or service. Filtering requires an O(n) scan and an additional O(k log k) sort for the matching records. More important than the individual operations was the trade-off: the unordered map provides efficient direct access but no useful ordering, while a vector provides an effective temporary sorted view. This work supports Outcome 3 because it demonstrates algorithmic reasoning, complexity analysis, validation, and evaluation of alternative designs.

Software Engineering and Databases

My software-engineering growth is visible in the progression from one procedural C++ file to a modular application. Client, InputValidator, AuthenticationService, ClientManager, AppController, and DatabaseManager each have focused responsibilities. The design is easier to test, maintain, and extend, and the small main function only starts the application and handles unexpected failure. The database enhancement added an SQLite schema for users, clients, and audit records. Prepared statements separate SQL from values, constraints protect stored data, foreign keys preserve relationships, and transactions keep client updates consistent with audit entries. CMake provides a repeatable build, while compiler warnings and iterative testing help identify issues before release. These practices support Outcome 4 by using well-founded tools and techniques to produce a practical solution with clear value.

Security Mindset

Security became part of the design process rather than a final checklist. The artifact validates complete input lines, restricts menu and service values, limits login attempts, returns failure codes when authentication is denied, and separates authentication from normal application flow. Database statements use bound parameters rather than constructing SQL from user input. Table constraints, foreign keys, transactions, rollback handling, and audit records provide additional protection and traceability. The project also documents what is not secure: the classroom password hash is simple, unsalted, and visible in source code, so it is not presented as production authentication. Recognizing and communicating that limitation is part of Outcome 5 because a security mindset includes anticipating misuse, exposing weaknesses honestly, and planning appropriate future controls.

The narratives explain why each enhancement was selected, what changed, what I learned, and how the work supports the course outcomes. Together, the artifacts show a progression from understanding existing code to designing, implementing, testing, securing, documenting, and presenting a more complete computing solution.
